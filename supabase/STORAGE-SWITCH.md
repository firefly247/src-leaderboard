# 데이터 이전 및 운영 저장소 전환

## 현재 운영 상태

사용자의 명시적 전환 지시에 따라 **2026-10-26 08:48:17 KST**에 `activateSupabaseStorage`를 실행했습니다. 최신 원본 938행을 재대조한 뒤 `CLUB_STORAGE_PROVIDER=supabase`로 설정했습니다. 전환 원본 커밋은 `7cf1b22ab879ee38142802a6d0f8413540142f7b`, DB 버전은 1입니다. 사진 54개는 모두 해상도를 유지하고 150KiB 이하로 압축했으며, 7,025,689바이트의 압축본을 비공개 버킷으로 복사하고 해시 검증을 마쳤습니다. 원본 ZIP 및 기존 비압축 클라우드 백업은 보존합니다. 전환 후 새로 연 실제 사이트에서 에르고 기록 150개, 대회 기록 화면 및 10/24·10/25 훈련 참가 명단이 정상 표시됨을 확인했습니다.

아래는 준비·전환 절차의 기록입니다. **운영 중에는 원본 재이전/활성화 함수를 다시 실행하지 않습니다.**

## 전환 전 작업 범위

기존 DB를 운영 저장소로 유지하면서 Supabase에 데이터를 복사·대조하고, 별도 지시를 받으면 안전하게 전환할 수 있게 준비합니다. 코드 작성이나 데이터 복사만으로 운영 DB가 바뀌지 않습니다.

2026-10-26에 두 SQL을 적용하고 Apps Script 웹 앱 버전 23 및 화면 버전 `20261026-02`를 배포했습니다. 같은 날 **08:27 KST**에 업무 테이블 12개의 총 938행을 복사하고 원본과 SHA-256 일치를 확인했습니다. 이 첫 복사 시점의 운영 저장소는 `sheets-and-csv`였으며, 이후 위에 기록한 시점에 Supabase로 전환했습니다. 08:32 KST에 사진 54개(9,325,922바이트)도 비공개 `club-proof-backup` 버킷으로 복사하고 모든 파일의 SHA-256 대조를 마쳤습니다. `CLUB_PROOF_REPORT`는 `complete:true`, `verifiedFiles:54`입니다. 웹사이트의 사진 주소는 GitHub를 계속 사용합니다.

## 배포 순서

1. `20261025130000_prepare_club_storage.sql`은 이미 프로젝트에 적용되어 있습니다. 재실행하지 않습니다.
2. `20261026060000_storage_switch.sql`을 한 번 적용합니다. 업무 테이블 12개는 유지하며, 저장 버전 메타 테이블 1개와 서버 전용 함수 `club_store_read`, `club_store_commit`을 추가합니다. 익명/일반 회원 접근 권한은 부여하지 않습니다.
3. Apps Script에 `StorageLayout.gs`, `StorageSwitch.gs`, `ProofMigration.gs`, `ProofDedup.gs`를 추가하고 `Code.gs`, `Training.gs`, `RaceLineup.gs`, `SupabaseStore.gs`를 업데이트합니다. 원격의 관련 없는 코드는 덮어쓰지 않고 먼저 백업·대조합니다.
4. 기존 웹 앱 배포를 새 버전으로 업데이트합니다. `CLUB_STORAGE_PROVIDER`를 설정하지 않으면 기본값은 `sheets-and-csv`입니다. 이 값을 수동으로 바꾸지 않습니다.
5. 웹 화면의 `leaderboard.js?v=20261026-02`을 배포합니다. 기존 저장소에서는 기존 CSV 조회를 유지하며, 전환 후에는 서버가 공개 데이터 8종만 전달합니다. 비공개 선수 정보·신청 이력·초안·수정키 해시는 공개 데이터 API에 포함하지 않습니다.

수동 SQL 적용 시 Supabase CLI migration 이력은 자동 등록되지 않습니다. 추후 CLI를 도입할 때 이미 적용된 두 SQL의 이력을 대조·기록한 후 후속 migration만 적용합니다.

## 지금 실행할 데이터 복사

Apps Script 소유자 편집기에서 다음 함수를 실행합니다. 공개 API에는 이전/전환 액션을 추가하지 않았습니다.

1. `migrateClubDataToSupabase`
   - GitHub의 한 커밋에 고정한 CSV 8종과 비공개 시트 4종을 읽습니다.
   - 알 수 없는 열·누락/중복 키·유효하지 않은 JSON이 있으면 중단합니다.
   - Supabase의 테이블 12개 중 원본과 다른 행만 한 트랜잭션으로 복사합니다. 신청 이력은 원본 JSON을 한 번 보관하는 8컬럼 구조로 저장하고 기존 화면용 필드는 조회 시 복원합니다. 충돌이나 어느 테이블의 오류가 발생하면 전체 쓰기가 롤백됩니다.
   - 다시 읽은 데이터와 원본을 SHA-256으로 대조하고, 원본이 도중에 변하지 않았는지 재확인합니다.
   - 원본은 삭제하지 않으며 운영 저장소 설정도 변경하지 않습니다. 원본이 계속 운영 중이므로 나중에 다시 동기화해야 합니다.
2. `migrateProofPhotoBatch`
   - 위에서 확인한 커밋의 `data/proofs/` 사진을 내용 해시로 중복 제거한 뒤 비공개 `club-proof-backup` 버킷에 10개씩 복사합니다.
   - 각 업로드를 다시 다운로드하여 SHA-256을 대조한 뒤에만 진행 상태를 기록합니다. 여러 번 실행해도 완료한 위치에서 이어갑니다.
   - 실행 로그의 `complete: true`, `verifiedFiles === totalFiles`를 확인합니다.
   - 기존 사진 URL과 업로드 경로는 계속 GitHub를 사용합니다. 사진 저장 서비스 전환은 이번 DB 전환에 포함하지 않습니다.
3. `clubStorageStatus`
   - 운영 저장소, 복사 시점, 건수, 원본 커밋, 대조 결과만 출력합니다. 개인정보나 키는 출력하지 않습니다.

개인정보·신청 원본·수정키 해시는 저장소나 채팅에 내보내지 않습니다. 복사는 기존 서버 안에서 등록된 서버 키를 사용하여 Supabase로 직접 수행합니다.

## 사용자가 나중에 전환을 지시하면

예: **“운영 DB를 Supabase로 전환해 줘.”**

그때 Apps Script 소유자 편집기의 **`activateSupabaseStorage`**를 실행합니다. 이 함수는:

1. 전환을 지원하는 프런트엔드가 실제 공개 사이트에 배포됐는지 확인합니다.
2. 같은 서버 잠금 아래에서 최신 원본을 다시 복사합니다. 이전 복사본이 오래됐어도 그대로 전환하지 않습니다.
3. 복사본과 최신 원본이 일치하는지 다시 대조합니다.
4. 모두 성공한 후에만 운영 설정을 `supabase`로 바꿉니다.

따라서 지금 별도로 “전환” 지시가 없으면 이 함수는 실행하지 않습니다. 전환 전에 열려 있던 화면은 새로고침합니다. 서버는 설정 변경 후의 요청부터 Supabase를 사용합니다.

## 전환 후 저장 안전성 및 한계

- 하나의 요청 안에서 기록과 승인 이력, 양일 참가 신청 등의 변경을 모두 메모리에 반영한 뒤 한 번에 커밋합니다. 실패한 요청은 부분 저장하지 않습니다.
- 서버 잠금과 DB의 저장 버전을 함께 확인합니다. 이전 버전으로 덮어쓰려는 요청은 거부합니다.
- Supabase 오류 시 예전 스프레드시트로 자동 대체 저장하지 않습니다. 두 저장소에 변경이 분산되지 않도록 오류를 표시합니다.
- 서버 요청마다 12개 데이터셋을 읽되, 저장할 때는 변경된 행의 추가/수정/삭제만 한 트랜잭션으로 전달합니다. 변경되지 않은 행은 다시 쓰지 않습니다. 데이터가 크게 늘면 읽기 범위도 기능별로 줄일 수 있습니다.
- 원본 시트와 CSV는 전환 당시 상태로 남습니다. **Supabase 운영 후 설정값만 옛 DB로 바꾸면 최신 변경을 잃을 수 있습니다.** 되돌리려면 최신 Supabase 데이터를 원본 쪽으로 역이전·대조하는 별도 작업이 필요합니다. 역전환 기능은 이번 작업에 포함하지 않습니다.
- Supabase Table Editor/SQL에서 앱 데이터를 직접 수정하면 저장 버전 추적을 우회합니다. 운영 중 변경은 앱의 관리자 기능으로 처리합니다.
- 서버 Secret key 및 기존 관리자 권한은 변경하지 않습니다. 카카오 로그인과 실명 연결은 별개의 기능입니다.

## 검증

```powershell
python scripts/prepare_storage_switch.py
python scripts/prepare_supabase.py --export-csv
node --test tests/*.test.js
node scripts/verify_supabase_schema.mjs <PGlite 모듈의 dist/index.js 경로>
```

실제 PostgreSQL 호환 엔진에서 12개 데이터셋의 원자적 커밋, 저장 버전 충돌, 후반 테이블 오류 시 전체 롤백, 역할별 함수 접근 차단을 검증합니다. 애플리케이션 테스트는 기존 저장소 유지, 전환 시점의 재복사·대조, 참가 신청/선수 연도/기록 승인/대회 초안, 실패 시 옛 DB로 저장하지 않는 동작을 확인합니다.
